# sendMail Project Constitution

## Core Principles

### I. Working Tree Stays Green (NON-NEGOTIABLE)
The full pre-commit suite must pass before any commit: pymarkdown, black, ruff,
vulture, pyright (0 errors), mypy --strict, and the pytest suite. A failing check
is fixed or explicitly reverted — never bypassed with `--no-verify`.
Note: `pre-commit-checks.sh` runs `tests/unit/` only; integration tests
(`tests/integration/`) MUST be run explicitly when touching the send pipeline,
filter logic, or database readers.

### II. Test-First for Behavioral Changes
Tests are written (and seen to fail) before the implementation that satisfies
them, following the existing layouts: `tests/unit/` for contracts and pure logic,
`tests/integration/` for send-pipeline and file-based workflows, behave/BDD for
user-visible scenarios. Existing tests encoding superseded behavior are updated
to the new contract, never weakened to pass.

### III. Reuse Before Reinvent
New features build on the existing engines (e.g. `format_message`,
`SchemaCacheProvider`, the Quill `runJavaScript` bridge) rather than introducing
parallel mechanisms. A new dependency requires explicit justification; a second
implementation of an existing capability is a design smell.

### IV. Recipient Data Isolation (NON-NEGOTIABLE)
A message addressed to several recipients must never contain any subscriber's
personal data — merge fields blank out, and any feature introducing per-recipient
content must force one-recipient-per-message batches. Credentials, tokens, and
the subscriber databases stay out of git (`.gitignore` discipline); secrets come
from the vault (`get-hc-secrets`), never from committed files.

### V. Behavior Fixes Must Trace to an Observed Failure
Bugs are reproduced by a failing automated test before fixing (red → green),
with the root cause recorded (spec `research.md` or commit message). Regression
tests are added for every user-reported defect.

### VI. Simplicity & In-Place Evolution
Smallest coherent change; no speculative abstractions, optional features, or
drive-by refactors. Public function signatures only change when necessary, with
defaults preserving existing callers.

## Additional Constraints

- **Language/versions**: Python 3.12–3.14, PySide6 ≥6.12; typing enforced via
  pyright strict and mypy strict (tool config in `pyproject.toml` is the source
  of truth).
- **User-facing behavior changes** require matching updates to `README.md` and
  `docs/TUTORIAL.md` in the same change; `CHANGELOG.md` is generated by
  commitizen from conventional commits — do not edit by hand.
- **macOS GUI**: Qt workarounds (AA_DontUseNativeDialogs, platform env vars)
  are load-bearing; changes to startup code require a GUI smoke test and a
  comment explaining the constraint.
- **Spec-driven features** follow the `/speckit.*` workflow (spec → clarify →
  plan → tasks → implement) with artifacts under `specs/NNN-name/`; artifacts
  are updated when the implementation diverges from them.

## Development Workflow

- Feature branches named `NNN-short-name` (spec-kit git extension); work lands
  on `beta`, merges to `master` via PR.
- Commits follow commitizen conventional-commit format with the Mistral Vibe
  trailer.
- External actions with shared blast radius (push, force-push, release, publish)
  require explicit user authorization each time; local commits are fine once the
  checks pass.

## Governance

This constitution is the reference for `/speckit.analyze` and code review.
Conflicts are resolved in favor of the NON-NEGOTIABLE principles; amendments
require editing this file explicitly (with version bump) — never silently
reinterpreted in specs or reviews.
